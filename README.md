# Women's Health Library

เว็บไซต์ภาษาไทยสำหรับผู้ป่วยอ่านทบทวนหลังพบแพทย์ พัฒนาด้วย Next.js 16, Payload CMS 3 และ PostgreSQL 17

## แนวทาง hosting งบ 0 บาท

ใช้เว็บ static บน GitHub Pages โดยเก็บ CMS ไว้ใช้ในเครื่องพัฒนา อ่าน `content/github-pages-guide.md` สำหรับการส่งออกและการเปิดเว็บภายหลัง การเปิดเว็บใช้ workflow แบบ manual และต้องเลือก publish อย่างชัดเจน

```sh
STATIC_BASE_PATH=/womens-health-library npm run static:preview
npm run serve:static
```

ตัวอย่างในเครื่องมีครบ 4 หน้า ส่วน `npm run static:export` ส่งออกเฉพาะบทความที่เผยแพร่แล้วใน CMS ไปยัง `out/` ตอนนี้สองบทความเป็นฉบับเริ่มต้นที่ผู้จัดทำอนุมัติเผยแพร่ โดยมีป้ายว่ายังไม่ได้ผ่านการตรวจทานทางการแพทย์

## ขอบเขตรุ่นแรก

- หน้าแรก `/` แสดงเฉพาะบทความที่เผยแพร่แล้ว
- บทความ `/articles/uterine-fibroids` และ `/articles/vaginal-discharge`
- เกี่ยวกับเว็บไซต์ `/about`
- ทีมงาน `/admin` และตัวอย่างร่างที่ต้องเข้าสู่ระบบ `/preview/<slug>`

การ seed สร้างบทความทั้งสองเป็น **ร่าง** ก่อนเสมอ ชุดเว็บสาธารณะปัจจุบันมีสองบทความที่อนุมัติเผยแพร่โดยผู้จัดทำ และระบุว่าไม่ใช่การตรวจทานทางการแพทย์ บทความเนื้องอกมดลูกนำเนื้อหาจากต้นแบบมาจัดเก็บ ส่วนตกขาวมีเนื้อหาฉบับร่างซึ่งยังต้องตรวจสอบแหล่งอ้างอิงและให้แพทย์ตรวจทาน ไฟล์ `index.html` เดิมเก็บไว้เป็นต้นแบบ ไม่มีการนำร่างนั้นขึ้นเว็บใหม่

## เริ่มพัฒนา

ต้องมี Node.js 24, npm และ Docker Compose ใช้ checkout ปัจจุบัน ไม่ต้องสร้าง worktree

```sh
npm ci
node scripts/setup-local.mjs
docker compose up -d --wait database
npm run seed
npm run dev
```

`setup-local.mjs` สร้าง `.env` สำหรับเครื่องพัฒนาด้วยค่าที่สุ่มและไม่พิมพ์ออกมา หากมีไฟล์แล้วจะรักษาค่าเดิมไว้ บน cloud นี้ หาก npm เขียน cache เริ่มต้นไม่ได้ ให้เพิ่ม `--cache /tmp/womens-health-npm` ในคำสั่งติดตั้ง

เปิด `/admin` ในเครื่องพัฒนา ข้อมูลเข้าสู่ระบบทดสอบครั้งแรกอยู่ใน `.local/admin-login.txt` ซึ่งถูก gitignore และตั้งสิทธิ์ไฟล์ 0600 ไม่ควรนำบัญชีทดสอบนี้ไปใช้จริง เปลี่ยนรหัสผ่านและสร้างบัญชีเฉพาะบุคคลก่อนใช้งานกับทีมงาน

Seed ทำซ้ำได้โดยไม่เขียนทับบทความหรือบัญชีเดิม เก็บฐานข้อมูลใน Docker volume และไฟล์อัปโหลดใน `media/` ซึ่งต้องสำรองแยกกัน

## เขียน ตรวจทาน และเผยแพร่

1. ผู้เขียนสร้างร่างและกรอกข้อมูล แล้วบันทึกร่าง (`Save Draft`) เลือกสถานะ `รอตรวจทาน` เมื่อพร้อม
2. ผู้ตรวจทานเปิดร่าง ตรวจเนื้อหาและอ้างอิง แล้วเลือก `อนุมัติ` และบันทึกร่าง ต้องมีสรุป เนื้อหา คำแนะนำอาการเร่งด่วน และแหล่งอ้างอิง
3. ผู้เผยแพร่เลือก `เผยแพร่` และใช้ปุ่ม Publish ระบบตรวจว่าเนื้อหาตรงกับเวอร์ชันที่อนุมัติแล้ว
4. เมื่อแก้ไข ให้บันทึกเป็นร่างใหม่ เวอร์ชันที่เผยแพร่เดิมยังแสดงอยู่ การเปลี่ยนเนื้อหาทำให้ต้องอนุมัติใหม่
5. ถอนบทความด้วย Unpublish โดยผู้เผยแพร่หรือผู้ดูแล ระบบหยุดแสดงบทความสาธารณะ

ใช้ปุ่ม Preview ในหน้าบทความเพื่อเปิดตัวอย่างสำหรับทีมงาน ต้องเข้าสู่ระบบก่อน และยังต้องบันทึกร่างก่อนดูตัวอย่าง

สิทธิ์: author เขียนและส่งตรวจ, reviewer ตรวจและอนุมัติ, publisher เผยแพร่/ถอน, admin จัดการทั้งหมด บัญชีทีมงานทุกบทบาทอ่านและแก้ร่างร่วมกันได้ ผู้ใช้ทั่วไปอ่านเฉพาะบทความที่เผยแพร่ ฟิลด์บทบาทแก้ได้เฉพาะ admin

เนื้อหาใช้ plain text และหัวข้อที่จัดลำดับได้ React escape ข้อความแทนการรับ HTML จาก editor ภาพอัปโหลดรับ JPEG/PNG/WebP และยังจำกัดเฉพาะทีมงาน รุ่นนี้ยังไม่ได้เชื่อมภาพอัปโหลดกับหน้าบทความสาธารณะ

## ตรวจสอบ

```sh
npm run typecheck
npm test
npm run build
npm run start
```

ทดสอบเบราว์เซอร์หลัง seed และ build:

```sh
npx playwright install chromium
npm run test:browser
```

บน cloud นี้มี Chromium อยู่แล้ว ใช้ `PLAYWRIGHT_CHROMIUM_PATH=/usr/bin/chromium npm run test:browser` ได้ การทดสอบตรวจหน้ามือถือ preview ที่ต้องเข้าสู่ระบบ และการเผยแพร่บทความทดสอบชั่วคราว โดยไม่อนุมัติบทความทางการแพทย์ตั้งต้น


Integration test ใช้ฐานข้อมูลจริง สร้างข้อมูลทดสอบเฉพาะแล้วลบเมื่อจบ ครอบคลุมสิทธิ์อนุมัติ/เผยแพร่ การแก้ไขหลังอนุมัติ การแยกร่างจากสาธารณะ การรักษาเวอร์ชันเดิม การถอนบทความ และการป้องกันยกระดับสิทธิ์ตนเอง ห้ามชี้ test ไปยังฐานข้อมูล production

Payload PostgreSQL adapter รุ่นนี้คง health connection ไว้หลัง destroy จึงใช้ Node test runner `--test-force-exit` หลัง test จบ ส่วน seed ออกจาก process หลังงานที่ await เสร็จทั้งหมด โดยไม่กลบข้อผิดพลาด

GitHub Actions มี typecheck, integration test, build และ browser test โดยใช้ PostgreSQL แยกสำหรับ CI ยังไม่ได้รันบน GitHub เพราะไม่มีการ push

## ก่อนใช้งานจริง

ยังไม่มีการ deploy มี initial migration ที่ทดสอบกับฐานข้อมูลใหม่แล้ว ยังต้องเตรียม HTTPS/hosting, email adapter สำหรับกู้รหัสผ่าน, สำรองและทดสอบกู้คืนฐานข้อมูล/ไฟล์ และยืนยันทีมผู้จัดทำ/ผู้ตรวจทาน เนื้อหาทั้งสองต้องผ่านการตรวจทางการแพทย์จริง การอนุมัติในระบบเป็นบันทึกของผู้ใช้งาน ไม่ใช่หลักฐานยืนยันคุณวุฒิแพทย์

## โครงสร้าง

- `src/app/(public)` หน้าเว็บผู้อ่านและตัวอย่างที่จำกัดสิทธิ์
- `src/app/(payload)` หน้า admin และ REST API
- `src/collections` Users, Articles, Media
- `src/globals/SiteSettings.ts` ข้อความหน้าแรก วัตถุประสงค์ ขอบเขตข้อมูล กระบวนการตรวจทาน และข้อมูลทีมผู้จัดทำ (แก้ได้เฉพาะ admin)
- `src/lib/workflow.ts` กฎการอนุมัติและ fingerprint ของเนื้อหา
- `scripts` การตั้งค่าเครื่องพัฒนาและข้อมูลตั้งต้น
- `tests` integration test

## เวอร์ชัน dependencies

ใช้ overrides สำหรับ Sass, Undici, DOMPurify และ esbuild ที่ dependency ย่อยตรึงรุ่นเก่าไว้ พร้อม Sharp รุ่นที่แก้ประกาศช่องโหว่แล้ว ต้องทดสอบ build และ workflow เมื่ออัปเดต Payload หรือเปลี่ยน overrides

## บทความตกขาวฉบับร่าง

ข้อมูลสำหรับ CMS อยู่ใน `content/articles/vaginal-discharge.json` และเอกสารสำหรับแพทย์ตรวจทานอยู่ใน `content/articles/vaginal-discharge-review.md` หน้าอ้างอิง NHS/CDC ยังไม่ได้ตรวจสอบจากเว็บไซต์จริงเนื่องจากข้อจำกัดเครือข่าย ต้องตรวจสอบก่อนอนุมัติ

สำหรับฐานข้อมูลที่มี placeholder เดิม ใช้ `npm run draft:discharge` เพื่อเติมเฉพาะร่างเดิมที่ยังไม่ได้แก้ไข สคริปต์จะไม่เขียนทับบทความที่ทีมงานแก้แล้ว และตรวจว่าร่างไม่ปรากฏต่อผู้ใช้ทั่วไป การ seed ในฐานข้อมูลใหม่จะสร้างเนื้อหานี้เป็นร่างโดยตรง

## ชุดเอกสารส่งแพทย์ตรวจทาน

```sh
PLAYWRIGHT_CHROMIUM_PATH=/usr/bin/chromium npm run review:export
```

หากใช้ Chromium ที่ติดตั้งผ่าน Playwright ให้ละตัวแปร `PLAYWRIGHT_CHROMIUM_PATH` สคริปต์อ่านร่างล่าสุดทั้งสองบทความจาก CMS แล้วสร้าง PDF รวม เอกสาร Markdown แยก และ snapshot พร้อมรหัสตรวจสอบเนื้อหาไว้ในโฟลเดอร์ใหม่ใต้ `.local/review/` โดยไม่เปลี่ยนสถานะบทความหรือสร้างการอนุมัติ และไม่เขียนทับข้อคิดเห็นในชุดเดิม

นำข้อแก้ไขของแพทย์กลับเข้า CMS ก่อนอนุมัติเวอร์ชันสุดท้าย หากเนื้อหาเปลี่ยนต้องส่งออกใหม่เพื่อให้เอกสารตรงกับเวอร์ชันที่ตรวจจริง

## Migration และสำรองข้อมูล

อ่าน `content/technical-handoff.md` สำหรับขอบเขตและวิธีใช้

```sh
npm run migrate:verify
npm run backup:local
npm run backup:verify -- .local/backups/<backup-directory>
```

Migration ทดสอบกับฐานข้อมูลว่างแยกต่างหาก การตรวจ backup กู้ลงฐานข้อมูลชั่วคราวและเทียบข้อมูลทุกตาราง ไม่เขียนทับฐานข้อมูลหลัก ห้ามรัน initial migration ทับฐานข้อมูลพัฒนาที่มี schema อยู่แล้ว

## การอนุมัติเผยแพร่กับการตรวจทานทางการแพทย์

`reviewCategory` บันทึกจากบทบาทของผู้อนุมัติ ไม่รับค่าที่ผู้เขียนส่งมา การอนุมัติโดย admin เป็น `editorial` และแสดงป้ายว่ายังไม่ได้ตรวจทางการแพทย์ ส่วนการอนุมัติโดยบัญชี reviewer เป็น `medical` ผู้ดูแลต้องมอบบทบาท reviewer ให้ผู้ตรวจทางการแพทย์จริง ระบบไม่ได้ตรวจสอบคุณวุฒิด้วยตัวเอง

สคริปต์ `node --import tsx scripts/publish-starter-articles.ts --editorial` ใช้กับสองบทความตั้งต้นตามคำสั่งผู้จัดทำเท่านั้น ไม่แก้เนื้อหา ไม่ลงชื่อแพทย์ และไม่เปลี่ยนการตรวจทางการแพทย์เดิม ใช้ใน CI เพื่อทดสอบข้อมูลจำลองด้วย

## ภาพประกอบบทความ

บทความเนื้องอกมดลูกมีภาพแผนผังที่สร้างขึ้นเพื่อการเรียนรู้ อยู่ที่ `public/illustrations/uterine-fibroids.png` ใช้ร่วมกันใน CMS และเว็บ static พร้อม alt text และคำบรรยายว่าไม่ใช่ภาพตรวจอัลตราซาวด์ ภาพยังอยู่ภายใต้สถานะบทความฉบับเริ่มต้นที่ไม่ได้ตรวจทานทางการแพทย์
